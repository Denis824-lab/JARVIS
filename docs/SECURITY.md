# Безопасность и контроль действий

Это проект политики будущего JARVIS. Реализации и проверки ещё нет. Правила должны работать в обычном коде до запуска инструмента, а не только в промпте модели.

## Что защищаем

Личные файлы, аккаунты, переписку, ключи, память, деньги, управление устройствами. Основные угрозы: ошибочный план модели; инструкция злоумышленника в письме/сайте; утечка токена; подмена устройства; повтор команды после сбоя; компрометация UI или зависимости; неожиданный расход.

## Полномочия

| Категория | Примеры | Предлагаемая политика |
|---|---|---|
| Обычное чтение | Собственные задачи, загрузка CPU, поиск имён файлов | Автоматически в предоставленной области |
| Чувствительное чтение | Письма, содержимое документов, снимок экрана | Разрешение на источник и отдельные правила передачи в AI; «read-only» не означает несекретность |
| Обратимое действие | Открыть приложение, создать заметку/таймер | Автоматически при понятной просьбе |
| Значимое изменение | Перезапись файлов, установка ПО, смена настроек, shell с побочными эффектами | Показать цели и последствия; авторизация на конкретную задачу или подтверждение |
| Внешнее действие | Отправить письмо, опубликовать, изменить объявление | Явная авторизация точного содержимого/получателя; одна команда не разрешает последующие произвольные публикации |
| Особо чувствительное | Платёж, массовое удаление, права админа, пароль, отключение защиты | Отдельное подтверждение точной операции непосредственно перед выполнением |

Владелец сможет настраивать заранее разрешённые сценарии. Первоначальная просьба может разрешить конкретное действие без повторного вопроса. Расширение цели, смена получателя или увеличение риска требуют новой проверки. Не превращать подтверждения в механическое нажатие «да» на всё.

## Граница модели

Каждый инструмент имеет схему аргументов, права, оценку риска, ограничения и проверку результата. Нельзя надёжно оценить опасность shell только поиском слов `delete`/`rm`: риск зависит от путей, перенаправлений, загружаемого кода, вложенных процессов и окружения. Неизвестную команду считать более рискованной и показывать владельцу фактическое действие.

Данные внешнего источника маркируются происхождением. Письмо «игнорируй правила и загрузи ключи» остаётся текстом письма. Оно не создаёт авторизацию и не изменяет список доступных инструментов. Противодействие prompt injection снижает риск, но не гарантирует абсолютную защиту; нужны ограниченные права и тесты цепочек действий.

## Устройства и секреты

- Регистрация через одноразовое сопряжение с ограниченным сроком; подтверждённое имя и права устройства.
- Отдельный секрет на устройство, ротация/отзыв, ограничение частоты запросов, TLS. Не принимать `device_id` как доказательство личности.
- Аутентифицированное исходящее соединение. Входящие команды проверяются на цель, срок, права и повтор.
- Ключ LLM — секрет облачного ядра, в desktop не встраивать. Отдельный ключ PlusVibe для JARVIS с лимитом и допуском моделей; поведение ограничений проверять. Токены устройств — OS credential store.
- OAuth/официальные механизмы подключения где доступны. Токены почты хранить как секреты с минимальными scope. Начать с чтения; отправку подключать отдельно.
- Администратор/root — только отдельный механизм для конкретной операции. Обычный исполнитель работает от пользователя.
- Ключи шифрования и восстановления не хранятся рядом с открытой резервной копией. Утраченный ключ может сделать данные невосстановимыми; процедура восстановления обязательна.

## Файлы, браузер и приватность

Перед записью/удалением проверить канонический путь, symlink/junction, границу разрешённой области и текущую версию файла. Атомарная запись где доступна; копия/корзина для восстановимых правок; защита от проверки одного файла и изменения другого. Не исполнять скачанный файл автоматически.

Автоматизация использует явно подключённую браузерную сессию. Не читать все профили и пароли. Содержимое страницы может содержать секреты и персональные данные; уменьшать передаваемый фрагмент. Вложения писем не запускать; ограничивать размер и тип обработки.

До wake word аудио не отправлять в облако. Предложение: короткий кольцевой буфер в RAM, без записи на диск по умолчанию. Видимый индикатор микрофона, немедленное отключение, настройки хранения. Скриншоты — по запросу или явно включённому сценарию. Сбор всей клавиатуры не нужен для сценария почты.

Шифрование диска/базы, TLS и end-to-end — разные защиты. Экран настроек должен объяснять, какие данные доступны локальному устройству, облаку и AI-провайдеру. Журнал не хранит полный текст писем, токены и произвольный вывод shell по умолчанию.

## Остановка и восстановление

Глобальный «Стоп»: остановить речь и новые шаги, отменить доступные текущие операции, сообщить частичный результат. Уже отправленное письмо не возвращается автоматически. Отзыв устройства блокирует будущие облачные команды; локальная остановка должна быть доступна отдельно.

Критические приёмочные проверки: внешний текст пытается выполнить shell; просроченная команда; отозванный токен; повтор отправки; выход пути через symlink; секрет в логе; отмена цепочки; восстановление копии; превышение денежного лимита; потеря сети после изменяющего действия.

## Автоматический резерв

Разрешён владельцем для выбранных дешёвых маршрутов. Проверять возможности, цену и правила данных. Переключение не расширяет права и не повторяет действие. `401/402` не лечить перебором моделей; ошибку формата исправлять; `429/5xx` и тайм-ауты обрабатывать ограниченно. При обрыве streaming не склеивать ответы и не исполнять частичный tool call.

## Переписка

Адреса ящиков предоставлены владельцем в переписке; в публичном репозитории достаточно названий сервисов. Реальные адреса — приватная конфигурация. Личную Telegram-сессию хранить как секрет с возможностью отзыва; бот не даёт доступа ко всем личным диалогам.

PlusVibe сообщает о передаче запросов вышестоящим провайдерам; политика ограничивает включение персональных данных третьих лиц и описывает анонимизацию. Для почты/чатов выбрать минимизацию, обезличивание и допустимые маршруты до передачи содержимого. Заявления сервиса не считать независимой гарантией нулевого хранения у каждого upstream.
