# Как понимать и сопровождать JARVIS

## Простой словарь

| Термин | Значение |
|---|---|
| UI | Окно, с которым ты взаимодействуешь |
| Исполнитель | Программа на компьютере, реально открывающая приложения и меняющая файлы |
| LLM | Модель, которая понимает запрос и предлагает действия; не сам компьютер |
| Инструмент | Конкретная функция с проверяемыми входами и результатом |
| Policy engine | Обычный код, решающий, разрешено ли действие |
| STT / TTS | Перевод речи в текст / текста в речь |
| API | Документированный способ обратиться к модели или сервису |
| Синхронизация | Передача изменений между устройствами |
| Миграция | Контролируемое изменение структуры сохранённых данных |
| ADR | Запись архитектурного решения: почему выбран этот вариант |

## Ритм разработки

Перед изменением агент объясняет один сценарий и связанные части системы. После изменения показывает результат и пишет, как проверить его самому. Ты должен уметь ответить: где выполняется действие, какие данные уходят наружу, почему оно разрешено и что делать при сбое.

Не требуется понимать каждую строку каждой библиотеки. Нужно понимать собственные модули, границы прав и потоки данных. Если агент предлагает новую технологию, он объясняет, какую конкретную проблему она решает и как её заменить.

## Что требовать в отчёте агента

1. Как изменилось поведение на конкретном примере.
2. Какие модули участвуют и где хранятся данные.
3. Как воспроизвести результат и какие проверки реально пройдены.
4. Что может сломаться, как заметить и восстановить.
5. Как изменились расходы и доступы.

Для существенного решения читай короткую запись в `docs/decisions/`, а не восстанавливай причину по длинной переписке. Текущий этап всегда указан в `docs/STATUS.md`.

## Наблюдаемость в самом продукте

Предусмотреть экран «Что произошло»: просьба → выбранное устройство → использованные инструменты → подтверждение → результат → стоимость. Это факты исполнения и краткое объяснение решения; внутренние рассуждения модели не нужны для контроля.

Отдельно: статус устройств, очередь, последняя синхронизация, доступность провайдера, ошибки, лимит бюджета и разрешения подключений. Диагностический экспорт очищается от секретов и личного содержимого; перед отправкой его можно просмотреть.

## Порядок диагностики

1. Проверить, принял ли JARVIS просьбу и правильно ли распознал текст.
2. Посмотреть выбранное устройство и его online-статус.
3. Проверить разрешение и возможное ожидание подтверждения.
4. Посмотреть фактический результат инструмента и его ошибку.
5. Проверить сеть, API и денежный лимит, если задача модельная.
6. Для памяти — поиск записи, очередь синхронизации, конфликт версий.

Реальные команды диагностики появятся с реализацией. Пока не существует программы, команды не выдумываем.

## Данные на годы

Экспорт и резервная копия — разные функции. Экспорт нужен для смены приложения/облака, копия — для восстановления после ошибки. Минимум одна копия хранится отдельно от рабочего устройства; шифрование и восстановление ключа документируются. Периодический тест восстановления важнее наличия кнопки «backup».
